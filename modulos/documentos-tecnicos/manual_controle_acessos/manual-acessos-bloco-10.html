Manual Operacional · Controle de Acessos · Bloco 10/10

Governança, Auditoria e
Checklist Final

Este bloco consolida as regras finais de governança, auditoria e revisão contínua dos acessos, garantindo que a matriz de permissões seja mantida após a implantação e não se degrade durante a operação.

1. Objetivo do Bloco 10

O objetivo deste bloco é definir como a No Fire deverá manter o controle de acessos após a configuração inicial.

A criação dos perfis, a vinculação de programas, a restrição por usuário e a revisão dos checkboxes não encerram o processo. O controle de acessos precisa ser mantido, revisado e corrigido sempre que houver mudança de usuário, função, responsabilidade ou risco.

Controle de acesso não é tarefa única. É rotina contínua de governança.

2. Princípio de manutenção

A No Fire deve considerar que o ambiente de acessos pode se degradar com o tempo se não houver revisão.

Isso pode ocorrer por:

  • criação de novos usuários;
  • mudança de função;
  • saída de colaboradores;
  • concessão de exceções;
  • marcação indevida de checkboxes;
  • liberação temporária que não foi removida;
  • uso de perfil administrador fora do necessário;
  • novas rotinas implantadas no sistema;
  • atualizações futuras do CAD ERP.

O risco não está apenas na configuração inicial. Está principalmente na falta de revisão depois.

3. Responsáveis pela governança

A governança de acessos deve ter responsáveis definidos. Sem responsável claro, o controle vira suposição.

Responsável Papel Limite
RH Cadastrar, atualizar e inativar usuários e funcionários. Não define perfil, programas, restrições ou checkboxes sensíveis.
Key User Configurar e revisar acessos conforme matriz. Não deve liberar exceções sem validação quando houver risco.
Gestão Validar acessos sensíveis, exceções e riscos assumidos. Deve evitar autorização informal sem registro mínimo.
Administrador Executar ações amplas quando necessário. Não usar acesso total como rotina comum sem critério.

Cada acesso deve ter dono, motivo e limite.

4. Eventos que exigem revisão de acesso

A revisão de acesso deve ocorrer sempre que houver alteração relevante na estrutura de pessoas ou funções.

Eventos obrigatórios de revisão:

  • entrada de novo colaborador;
  • alteração de cargo ou função;
  • transferência de setor;
  • desligamento;
  • retorno de usuário inativo;
  • concessão de acesso temporário;
  • criação de novo perfil;
  • alteração de perfil existente;
  • identificação de erro de acesso;
  • atualização do sistema;
  • mudança de processo operacional.

Mudou a função, revisa o acesso. Saiu da empresa, inativa. Recebeu exceção, registra.

5. Checklist de criação de usuário

Todo novo usuário deve passar por uma conferência mínima antes de ser considerado liberado para operação.

  1. Funcionário foi cadastrado ou localizado corretamente?
  2. Usuário foi criado na PBCA035C?
  3. Dados cadastrais foram conferidos?
  4. Função do usuário foi confirmada?
  5. Perfil correto foi identificado?
  6. Perfil foi criado na PBCA079, se necessário?
  7. Programas foram vinculados na PBCA079A?
  8. Usuário foi revisado na PBCA035?
  9. Checkboxes da PBCA035C foram revisados?
  10. Permissões críticas foram bloqueadas quando não aplicáveis?
  11. Exceções foram validadas?
  12. Usuário foi comunicado como pronto para uso?

Usuário criado não é usuário liberado. Usuário só está pronto após revisão completa.

6. Checklist de inativação de usuário

A inativação é tão importante quanto a criação. Usuário que não deveria mais acessar o sistema não pode permanecer ativo.

  1. Usuário correto foi identificado?
  2. Funcionário correspondente foi localizado?
  3. Situação do usuário foi alterada para inativo?
  4. Situação do funcionário foi ajustada quando aplicável?
  5. Foi conferido se não existe usuário duplicado?
  6. Gestão foi informada da inativação?
  7. O acesso deixou de aparecer como ativo?

Usuário desligado ou sem função ativa não deve permanecer habilitado no sistema.

7. Checklist de revisão mensal

Recomenda-se executar uma revisão periódica da base de usuários e acessos.

Na revisão mensal, verificar:

  1. Lista de usuários ativos.
  2. Usuários que deveriam estar inativos.
  3. Usuários com perfil administrador.
  4. Usuários sem perfil ou com perfil incorreto.
  5. Usuários com permissões financeiras.
  6. Usuários com permissões fiscais.
  7. Usuários com acesso a exportação de dados.
  8. Usuários com acesso a perfil, vinculação e restrição.
  9. Checkboxes críticos marcados.
  10. Exceções concedidas no mês.
  11. Acessos temporários ainda ativos.

Revisão mensal evita que exceção temporária vire acesso permanente.

8. Checklist de revisão por perfil

Além da revisão por usuário, os perfis também devem ser revisados periodicamente.

  1. O perfil ainda representa uma função real?
  2. Existem usuários associados ao perfil?
  3. Os programas vinculados continuam corretos?
  4. Algum programa crítico foi incluído sem justificativa?
  5. Algum programa financeiro foi incluído indevidamente?
  6. Algum programa fiscal foi incluído indevidamente?
  7. O perfil está sendo usado para exceções individuais?
  8. Há perfis duplicados ou parecidos demais?
  9. Há perfil que deveria ser descontinuado?

Perfil também envelhece. Se não for revisado, vira risco acumulado.

9. Controle de exceções

Exceção é qualquer acesso fora do padrão previsto para o perfil do usuário.

Uma exceção pode ser necessária, mas deve ser controlada.

Toda exceção relevante deve conter:

  • nome do usuário;
  • perfil atual;
  • programa ou checkbox liberado;
  • motivo da liberação;
  • responsável pela validação;
  • prazo, quando temporária;
  • data de revisão.

Exceção sem registro não é exceção. É descontrole.

10. Acessos que exigem registro obrigatório

Algumas liberações são sensíveis o suficiente para exigir registro mínimo sempre que ocorrerem.

  • perfil administrador;
  • acesso à PBCA035;
  • acesso à PBCA079;
  • acesso à PBCA079A;
  • acesso à exportação de dados;
  • acesso a programas financeiros;
  • acesso a programas fiscais;
  • acesso a parâmetros do sistema;
  • checkbox de alteração de valor;
  • checkbox de alteração de desconto;
  • checkbox de cancelamento de pedido;
  • checkbox de exclusão de pedido;
  • checkbox de cancelamento de nota fiscal.

Quanto maior o poder concedido, maior deve ser o rastro da decisão.

11. Tratamento de acesso indevido

Caso seja identificado acesso indevido, o procedimento não deve ser improvisado.

  1. Identificar o usuário.
  2. Identificar a tela ou programa acessado.
  3. Verificar se o acesso foi direto, por perfil, por restrição ou por caminho indireto.
  4. Verificar se houve alteração, exclusão, exportação ou apenas visualização.
  5. Bloquear ou ajustar a permissão quando possível.
  6. Revisar checkboxes relacionados.
  7. Registrar o ocorrido.
  8. Comunicar gestão quando houver risco relevante.
  9. Revisar se outros usuários possuem a mesma exposição.

Acesso indevido não deve ser tratado só no usuário afetado. Deve-se verificar se o problema é estrutural.

12. Auditoria de acessos indiretos

Como o sistema pode permitir acessos indiretos, a auditoria não deve olhar apenas menus e perfis.

Também deve verificar:

  • botões com acesso a outras telas;
  • atalhos internos;
  • rotinas abertas a partir de orçamento ou pedido;
  • relatórios externos ou BI;
  • utilitários acessíveis fora do fluxo principal;
  • cadastros estruturais acessados por telas operacionais.

O usuário pode não ter o menu, mas ainda assim alcançar a tela por outro caminho.

13. Regra de ouro para usuários

Todos os usuários devem ser orientados com uma regra simples:

Se a tela abriu, mas a função não pertence ao seu trabalho, não use.

O usuário deve entender que botão disponível não significa permissão operacional.

Em caso de dúvida:

  • não alterar;
  • não excluir;
  • não exportar;
  • não cancelar;
  • não aprovar;
  • não improvisar;
  • consultar o responsável.

14. Regra de ouro para key user

O key user deve seguir outra regra:

Acesso deve ser concedido pelo mínimo necessário, não pelo máximo possível.

Na prática:

  • liberar apenas o necessário;
  • bloquear o que não pertence à função;
  • desmarcar checkbox sem justificativa;
  • evitar perfil administrador como atalho;
  • documentar exceções;
  • revisar depois.

16. Frequência recomendada de auditoria

Tipo de revisão Frequência recomendada Objetivo
Usuários ativos Mensal Identificar usuários indevidos, duplicados ou inativos.
Administradores Mensal Confirmar se acesso total ainda é necessário.
Financeiro / fiscal Mensal Evitar acessos críticos indevidos.
Perfis e programas Trimestral Revisar matriz e remover excessos.
Checkboxes críticos Mensal Confirmar que permissões internas continuam justificadas.
Exceções Mensal Remover liberações temporárias vencidas.

Auditoria simples feita todo mês é melhor que auditoria perfeita nunca feita.

17. Encerramento do manual

Este manual estabelece a estrutura operacional de controle de acessos do CAD ERP na No Fire.

O sistema apresenta camadas técnicas de controle, mas também limitações, comportamentos permissivos e riscos que exigem governança compensatória.

Portanto, a operação segura depende da combinação entre:

  • cadastro correto de usuários;
  • perfis bem definidos;
  • programas vinculados com critério;
  • restrição por usuário;
  • checkboxes revisados;
  • controle de exceções;
  • auditoria recorrente;
  • responsabilidade individual.

O controle do ambiente não está apenas no CAD ERP. Está na disciplina de uso, revisão e governança da No Fire.
